**Key differences:**

- **Ordering:** Opus declared explicit dependency chains (build → config → entities → services → endpoints → cleanup) and execution followed this sequence faithfully. Sonnet declared step-level dependencies but the execution ran steps out of sequence — 13 steps vanished entirely from the log.
- **Reference usage:** Opus applied patterns from `javaee-quarkus.md` correctly, though it still picked the wrong REST artifact name. Sonnet used an outdated Quarkus version (3.0.0.Final) and the wrong extension name — indicating shallower reference consultation.

**Pattern:** Opus invests more in plan *structure* (ordering, dependency tracking) while Sonnet produces broader *coverage*. For migration tasks, structure matters more — proper ordering prevents cascading failures.

### Analysis

**Sonnet is faster at planning but pays for it later.** Sonnet generates a plan in 170s (vs Opus's 273s) — 38% faster. But the shallower plan leads to 13 execution failures and 3 verification fix cycles consuming 251s. Opus invests 103 more seconds in planning but saves 89s in execution and 195s in verification — a net savings of 181 seconds.

**Verification is where quality pays off.** Opus's verify phase is 4.5× faster (56s vs 251s) because it entered verification with only minor issues (artifact name, cascading dependency). Sonnet entered verification with Quarkus version issues, wrong plugin groupIds, wrong extension names, missing dependencies, and residual namespace problems — requiring 3 rounds of diagnosis and repair.

**There is no trade-off here.** Opus is not "slower but higher quality" — it is *both faster and higher quality*. The extra planning time is more than recouped by cleaner execution and faster verification. This is the ideal outcome: invest upfront, save downstream.

### Recommendation for JavaEE → Quarkus Migrations

- 12.7% higher overall score (8.0 vs 7.1)

## 5. Skill Improvement Recommendations

Based on failures observed across **both** models, the following skill file updates are recommended.

### 5.1 Critical: Reactive Messaging Channel Naming (Both Models Failed)

**Evidence:**
- Sonnet: Both MDBs use `@Incoming("orders")` while `application.properties` defines `inventory-notifications` and `order-topic` — complete mismatch causing guaranteed runtime failure.
- Opus: Both MDBs use `@Incoming("orders-incoming")` — consistent but creates a broadcast concern since two consumers share one channel without `broadcast=true`.

**Root cause:** The `javaee-quarkus.md` reference likely provides the *pattern* for MDB→Reactive Messaging conversion but does not enforce the *cross-file validation* step — checking that `@Incoming("X")` values match `mp.messaging.incoming.X.*` entries in `application.properties`.

**Recommended update to `javaee-quarkus.md`:**
```markdown
### MDB → Reactive Messaging: Channel Naming Rules

1. Each `@Incoming("channel-name")` MUST have a matching 
   `mp.messaging.incoming.channel-name.*` block in application.properties
2. Each `@Outgoing("channel-name")` MUST have a matching 
   `mp.messaging.outgoing.channel-name.*` block
3. If multiple consumers need the same messages, EITHER:
   a. Use separate channels with separate topic subscriptions, OR
   b. Add `mp.messaging.incoming.channel-name.broadcast=true`
4. VERIFICATION STEP: After converting all MDBs, run:
   `grep -r '@Incoming\|@Outgoing' src/ | sed 's/.*@\(Incoming\|Outgoing\)("\(.*\)").*/\2/' | sort -u`
   Cross-check every channel name against application.properties entries.
```

### 5.2 Critical: Quarkus Artifact Version Mapping (Both Models Failed)

**Evidence:**
- Both models used `quarkus-rest-jackson` which only exists in Quarkus ≥ 3.9.
- Sonnet used Quarkus 3.0.0.Final (outdated); Opus used 3.8.4 — both had the same artifact name error.

**Root cause:** Models conflate knowledge across Quarkus versions. The REST extension was renamed from `quarkus-resteasy-reactive-jackson` to `quarkus-rest-jackson` in Quarkus 3.9.

**Recommended update to `javaee-quarkus.md`:**
```markdown
### Quarkus Version-Specific Artifact Names

| Artifact (≤3.8) | Artifact (≥3.9) | Notes |
|---|---|---|
| quarkus-resteasy-reactive | quarkus-rest | Renamed in 3.9 |
| quarkus-resteasy-reactive-jackson | quarkus-rest-jackson | Renamed in 3.9 |
| quarkus-resteasy-reactive-jsonb | quarkus-rest-jsonb | Renamed in 3.9 |

**Target version guidance:** Use the latest LTS release. As of 2026, 
use Quarkus 3.8.x (LTS) or 3.15.x (LTS). Avoid non-LTS versions 
for production migrations. Always verify artifact names against the 
target version's BOM.
```

### 5.3 High: Dependency Removal Cascade Scanning (Opus Failed, Sonnet Avoided)

**Evidence:**
- Opus removed `audit-logging-library` from pom.xml but left `AuditConfiguration`, `AuditLoggingException`, and `FileSystemAuditLogger` references in `OrderService.java` — causing a compilation failure fixed in auto-fix iteration 2.
- Sonnet kept the audit library as-is, avoiding the issue pragmatically.

**Root cause:** The migration plan treats dependency removal as a pom.xml-only operation without scanning for code-level usages.

**Recommended update to `javaee-quarkus.md`:**
```markdown
### Removing App-Server or Vendor Dependencies

When removing a dependency from pom.xml:
1. BEFORE deleting the dependency entry, run:
   `mvn dependency:tree | grep <artifact-id>` to identify transitive consumers
2. Grep for all imports from the removed library:
   `grep -rn "import.*<package-prefix>" src/`
3. For each file with matching imports:
   - If the usage is dead code (e.g., initialization that's now handled by Quarkus): DELETE the code
   - If the usage is active: REPLACE with a Quarkus-native equivalent
4. Only THEN remove the dependency from pom.xml
```

### 5.4 High: Dead Code Removal After DI Conversion (Sonnet Failed)

**Evidence:**
- Sonnet left a dead `lookupShippingServiceRemote()` JNDI method with `javax.naming` imports in `ShoppingCartService.java` after converting the class to use `@Inject`.
- Opus correctly identified and handled this via cross-step lesson linking (Step 22 → Steps 20, 21).

**Root cause:** The skill teaches the `@EJB` → `@Inject` annotation swap but doesn't explicitly instruct removal of manual JNDI fallback methods that become dead code after DI conversion.

**Recommended update to `javaee-quarkus.md`:**
```markdown
### EJB → CDI: Complete Cleanup Checklist

After converting `@EJB` → `@Inject`:
1. Search the same file for `InitialContext`, `Context.lookup`, `JNDI`, 
   `PortableRemoteObject.narrow` — these are JNDI manual lookup fallbacks
2. Delete any private methods that perform manual EJB lookup
3. Remove `javax.naming.*` imports
4. Remove any try/catch blocks that caught `NamingException`
5. VERIFY: `grep -rn 'javax.naming\|InitialContext\|JNDI' src/` should return zero results
```

### 5.5 High: Post-Migration Test Generation (Both Models Failed)

**Evidence:**
- Both models: 0/0 tests. `maven.test.skip=true` in both. Neither model created any tests.
- Sonnet eval report: "For a 32-step migration touching 27 files, this is a significant risk."
- Opus eval report: "the lack of even basic integration tests is a risk."

**Root cause:** The migration skill has no step for test creation. Both models follow the plan exhaustively for code transformation but neither proactively adds tests.

**Recommended update to `javaee-quarkus.md`:**
```markdown
### Post-Migration: Minimum Test Requirements

After completing all migration steps and achieving BUILD SUCCESS:

1. Remove `<maven.test.skip>true</maven.test.skip>` if present
2. Add `quarkus-junit5` test dependency
3. Create a startup smoke test:
   ```java
   @QuarkusTest
   class ApplicationStartupTest {
       @Test
       void applicationStarts() {
           // If this test passes, the CDI injection graph is valid
           // and the application boots without errors
       }
   }
   ```
4. For each REST endpoint, create a basic response test:
   ```java
   @Test
   void testEndpointResponds() {
       given().when().get("/api/endpoint")
              .then().statusCode(anyOf(is(200), is(204)));
   }
   ```
5. Run `mvn test` and verify all tests pass
```

### 5.6 Medium: Execution Logging for Failed Steps (Sonnet Infrastructure Gap)

**Evidence:**
- Sonnet: 13 of 32 steps have zero trace in the execution log. Metrics say `items_failed: 13` but no error messages, no failure reasons, no diagnostic trail.
- Opus: 3 skipped steps all have documented justification.

**Root cause:** This appears to be a harness-level issue rather than a skill issue. The execution harness may not log failures before retrying or deferring to auto-fix.

**Recommended update to execution harness:**
```
For every step, log BOTH success and failure entries with:
- Step number and description
- Status: ok | failed | skipped
- If failed: error message, stack trace excerpt, file path
- If skipped: justification
```
