**Analysis:**

### Recommendation for JavaEE → Quarkus Migrations

**Use Claude Opus 4.6.** It is simultaneously the fastest overall (18m vs 21m) and produces the highest quality output (8.0 vs 7.1 vs 5.5). The extra investment in planning time (4.6 min vs 2.8 min for Sonnet, vs 1.2 min for Gemini) translates directly into fewer execution failures and dramatically less verification/fix time.

If Opus is unavailable, **Claude Sonnet 4 is a reasonable fallback** — it achieves a clean build with correct architectural patterns, but expect to spend additional time on the 13 untraced step failures and residual issues (channel naming, dead code).

**Gemini 2.5 Pro is not recommended** for this migration type — the missing `application.properties` is a showstopper, the CDI scope error is a functional bug, and the overall output requires 4-6 hours of additional work vs 1-2 hours for the Claude models.

## 5. Skill Improvement Recommendations

### Failures Common to ALL Three Models

#### 5.1. Reactive Messaging Channel Naming / Multi-Consumer Topology

**Evidence:**
- **Sonnet 4:** Both MDBs use `@Incoming("orders")` — doesn't match `application.properties` channel names (`inventory-notifications`, `order-topic`). Plan specified correct names but execution ignored them.
- **Opus 4.6:** Both MDBs use `@Incoming("orders-incoming")` — flagged the broadcast concern in a lesson but didn't resolve it. No `broadcast=true` configured.
- **Gemini 2.5 Pro:** Both MDBs use `@Incoming("orders")` — would cause SmallRye deployment failure.

**Root cause:** The `javaee-quarkus.md` reference doesn't enforce channel naming discipline or address the one-consumer-per-channel constraint in SmallRye Reactive Messaging.

**Recommended skill update to `javaee-quarkus.md`:**
```
## Reactive Messaging — Channel Naming Rules

1. Each @Incoming channel name MUST match a `mp.messaging.incoming.<name>` key 
   in application.properties. Cross-check after every MDB conversion.
2. SmallRye allows only ONE consumer per channel by default. If multiple MDBs 
   subscribed to the same JMS topic, you MUST either:
   a. Use distinct channel names with separate connector configs, OR
   b. Set `mp.messaging.incoming.<channel>.broadcast=true`
3. Verification step: `grep -r '@Incoming' src/ | awk -F'"' '{print $2}' | sort | uniq -c`
   — any count > 1 requires broadcast config or channel separation.
```

#### 5.2. Zero Test Generation

**Evidence:**
- **Sonnet 4:** 0/0 tests, `maven.test.skip=true` in pom.xml
- **Opus 4.6:** 0/0 tests, noted as a gap but no tests created
- **Gemini 2.5 Pro:** 0/0 tests, `maven.test.skip=true` hardcoded

**Root cause:** No migration reference step mandates post-migration test creation. All models treated "it compiles" as sufficient verification.

**Recommended skill update to `javaee-quarkus.md`:**
```
## Post-Migration Testing (MANDATORY)

After all code transformations:
1. Remove any `maven.test.skip=true` from pom.xml properties
2. Add `quarkus-junit5` test dependency
3. Create minimum smoke test:
   - @QuarkusTest class that verifies application starts
   - One REST endpoint test per endpoint class
   - CDI injection validation for all @ApplicationScoped beans
4. Verification: `mvn test` must pass with ≥1 test executed
```

#### 5.3. Quarkus REST Extension Artifact Naming

**Evidence:**
- **Sonnet 4:** Used `quarkus-rest-jackson` (wrong) → fixed to `quarkus-resteasy-reactive-jackson` during auto-fix
- **Opus 4.6:** Used `quarkus-rest-jackson` (wrong for 3.8.4) → fixed during auto-fix
- **Gemini 2.5 Pro:** Used correct artifact name initially

**Root cause:** The REST artifact was renamed between Quarkus 3.8 and 3.9. Models trained on mixed documentation confuse the two.

**Recommended skill update to `javaee-quarkus.md`:**
```
## Quarkus REST Extension Names (Version-Dependent)

| Quarkus Version | REST Extension Artifact |
|---|---|
| 3.0 – 3.8.x | quarkus-resteasy-reactive-jackson |
| 3.9+ | quarkus-rest-jackson |

Always verify artifact name against the target `quarkus.platform.version` in pom.xml.
```

#### 5.4. Dead Code / Dependency Cascade Removal

**Evidence:**
- **Sonnet 4:** Left dead `lookupShippingServiceRemote()` JNDI method with `javax.naming` imports in `ShoppingCartService.java`
- **Opus 4.6:** Removed audit-logging JAR from pom.xml but missed code references in `OrderService.java` (caught in fix loop)
- **Gemini 2.5 Pro:** Flagged JNDI removal as needed in Step 28 lesson but didn't execute it. Left stale `jboss-rmi` and `flyway-core` dependencies.

**Root cause:** Models handle direct annotation/import transformations well but consistently miss second-order effects: removing a dependency creates orphan imports; converting `@EJB` to `@Inject` leaves behind manual JNDI fallback code.

**Recommended skill update to `javaee-quarkus.md`:**
```
## Dependency Removal Cascade

When removing any dependency from pom.xml:
1. `grep -rn` for all imports from that dependency's packages across src/
2. For each file with matching imports: remove the import AND any code that 
   references the imported classes (dead methods, field declarations, etc.)
3. After converting @EJB → @Inject: search for JNDI lookup helper methods 
   (InitialContext, lookup(), narrow()) and remove them entirely

Verification: `mvn clean compile` must pass after dependency removal.
```

#### 5.5. `application.properties` Completeness Verification

**Evidence:**
- **Sonnet 4:** Created `application.properties` but with channel names that don't match `@Incoming` annotations
- **Opus 4.6:** Created complete `application.properties` (best of the three)
- **Gemini 2.5 Pro:** Planned but never created `application.properties` — step marked "ok" but file doesn't exist on disk

**Recommended skill update to `javaee-quarkus.md`:**
```
## Configuration File Verification (Post-Migration)

After creating application.properties:
1. Verify file exists: `test -f src/main/resources/application.properties`
2. Cross-check datasource config: grep for @PersistenceContext → ensure 
   quarkus.datasource.* entries exist
3. Cross-check messaging config: for each @Incoming/@Outgoing annotation value, 
   verify matching mp.messaging.incoming.*/outgoing.* entries
4. Cross-check Flyway: if quarkus-flyway is a dependency, ensure 
   quarkus.flyway.migrate-at-start=true is set
```
